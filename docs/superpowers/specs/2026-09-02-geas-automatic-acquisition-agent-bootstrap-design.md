# Geas Automatic Acquisition and Agent Bootstrap Design

**Date:** 2026-09-02

**Status:** Approved in design discussion; ready for implementation planning

**Scope:** Automatic source acquisition and extraction, delegated repository and
source authority, agent bootstrap, and repository publication

## Summary

Geas will turn checked-in ontology source declarations into a bounded,
resumable acquisition and extraction workflow while preserving its existing
authority direction. An ontology repository may state what it wants researched,
but only trusted local configuration may authorize network access, storage,
model use, Git mutation, or delegation of those capabilities.

The same deterministic capability evaluator will authorize repository
ontologies, external sources, pull-request publication, direct pushes, and
delegated authority. Agent installation and confined local bootstrap writes are
authorized by the explicit command invocation that names them; repository
content can never trigger that command. GitHub repository snapshots become one
acquisition adapter among several instead of a special ontology-build path.

Repository-backed agent installation will become a first-class transaction. It
can install Geas when absent, subscribe to and trust a requested ontology
repository, install the generic Geas skill, export ontology skills, and link
supported coding agents. It will announce each mutation before performing it,
record exact ownership receipts, and support deterministic update and removal.
Pull requests remain the publication default. Direct push requires both an
explicit invocation flag and a matching trusted local capability.

This design extends the repository catalog and portable skill designs in:

- `2026-08-28-geas-repository-catalog-trust-design.md`; and
- `2026-08-26-geas-agent-skill-export-design.md`.

Their catalog hashing, cumulative `geas.yaml` behavior, static skill snapshot,
path confinement, and repository-trust invariants remain in force. Where those
specifications say that skills never install Geas or publish changes, this
design supersedes that statement only for the explicit bootstrap and publishing
commands described below. Ordinary skill reading and `skill-export` remain
side-effect free beyond their documented managed files.

## Goals

1. Retrieve and preserve declared web documents automatically when trusted
   local policy permits it.
2. Feed newly acquired document versions into source libraries, structural
   anchoring, and proposal-only extraction without operator glue code.
3. Refresh news and slower-changing reference material on separate,
   deterministic schedules.
4. Use one capability model for local authority and bounded cross-repository
   delegation.
5. Make repository-backed Geas installation and skill setup straightforward for
   coding agents while keeping every mutation explicit and reversible.
6. Support pull-request publication by default and explicitly authorized direct
   push when requested.
7. Document a safe independent GitHub App pattern for deterministic artifact
   approval and automatic merge.
8. Make results, denials, resumptions, generated bytes, and tests deterministic.

## Non-goals

- Retrieved text, model output, a repository catalog, or a delegated repository
  cannot grant itself authority.
- Geas will not bypass authentication, paywalls, robots controls, anti-bot
  systems, or JavaScript challenges.
- This work does not add a browser automation acquisition adapter.
- This work does not make model-generated knowledge canonical without the
  existing verified Git promotion boundary.
- This work does not make `--yolo` a universal policy bypass.
- This work does not give an ontology repository access to local secrets,
  provider configuration, budgets, or arbitrary destinations.
- Nostr signatures are a future extension. Version one binds canonical bytes
  with SHA-256 and Git identity; it does not claim cryptographic authorship.
- Geas does not implement repository branch protection or forge approval rules.
  It emits and verifies artifacts that an independently configured forge policy
  may approve and merge.

## Governing authority model

### Authority still flows one way

The extended workflow is:

```text
trusted local configuration
  -> effective capability decision
  -> repository source intent and verified catalog bytes
  -> immutable acquisition records and source blobs
  -> parsed text and exact structural anchors
  -> proposal-only extraction
  -> verified Git promotion
  -> truth snapshot and projections
  -> exported skills and answers
```

Checked-in source intent is data evaluated under local policy. It cannot modify
the policy evaluator, credentials, budgets, workflow transitions, or Git
authority. A model receives selected inert text and strict output schemas only.

### Capability vocabulary

Version one defines these independently grantable capabilities:

| Capability | Permitted effect |
|---|---|
| `repository.read` | Verify and use catalog-declared repository bytes |
| `trust.delegate` | Evaluate a hash-pinned child delegation manifest |
| `source.discover` | Query the declared connector or enumerate a feed/sitemap |
| `source.fetch` | Perform a bounded network retrieval |
| `source.archive` | Persist eligible original response bytes and metadata |
| `source.extract` | Parse, structure, index, and select anchors locally |
| `model.external` | Send an authorized data class to an authorized external model |
| `git.pull_request` | Publish a generated branch and open/update a PR |
| `git.auto_merge` | Request auto-merge for an eligible deterministic PR |
| `git.direct_push` | Push generated changes directly to an authorized ref |
| `knowledge.auto_promote` | Allow independent automation to merge verified knowledge promotions |

`source.extract` does not imply `model.external`; local deterministic parsing
and indexing can proceed without a model. `git.auto_merge` does not imply
`knowledge.auto_promote`. Full repository read trust does not imply any network,
model, delegation, or write capability.

### Trusted local grants

The selected profile in the OS-standard Geas `config.yaml` is the only root of
authority. Configuration version 2 adds `capability_grants`. Existing version 1
ontology `trust_rules` load compatibly as `repository.read` grants and are
written as version 2 only by an explicit config update. The strict version 2
field names and shape are:

```yaml
version: 2
profiles:
  default:
    capability_grants:
      - decision: allow
        subject:
          repository: https://github.com/example/ontologies
          refs:
            - refs/heads/main
          paths: "*"
          bundle_sha256: "*"
        capabilities:
          - repository.read
          - trust.delegate
          - source.discover
          - source.fetch
          - source.archive
          - source.extract
          - git.pull_request
        delegable_capabilities:
          - repository.read
          - source.discover
          - source.fetch
          - source.archive
          - source.extract
        resources:
          delegated_repositories:
            - https://github.com/example/source-catalog
          hosts:
            - sedarplus.ca
            - example-miner.com
          path_prefixes: "*"
          connectors:
            - direct-https
            - rss-atom
            - sitemap
          providers: []
          models: []
          data_classes: []
          git_refs:
            - refs/heads/main
        max_delegation_depth: 1
        expires_at: null
        created_at: 2026-09-02T00:00:00Z
        created_via: manual
```

`subject.repository`, `decision`, `capabilities`, `delegable_capabilities`,
`resources`, `max_delegation_depth`, `expires_at`, `created_at`, and
`created_via` are required. `delegable_capabilities` must be a subset of
`capabilities`; it may be empty. `subject.refs`, `subject.paths`,
`subject.bundle_sha256`, and the resource collection fields accept `"*"` or a
sorted list; subject selector lists must be non-empty, while an empty resource
list means no resources of that class. Providers, models, and data classes
constrain `model.external`; Git refs constrain all Git write capabilities. All
fields are explicit on serialization, including empty lists and nulls.
Selectors are normalized and sorted before hashing or comparison. A grant
cannot contain embedded credentials or private-network resource identities.
Secrets remain named and loaded only through existing local allowlists.
`created_via` is one of `interactive`, `manual`, or `repository_install`.

The subject repository is the repository receiving a root-local grant. It is
not also a resource selector. `resources.delegated_repositories` is the closed
set of child repository identities to which that subject may delegate. The
other resource fields are the maximum source and operation scope that any child
may receive. A direct local grant for repository B names B as its subject; a
grant rooted at A that permits `A -> B` names A as its subject and B under
`delegated_repositories`.

The default maximum delegation depth is `1`. Depth counts delegation edges:
local configuration to repository A is the root grant, A to B is one edge, and
B to C is two. A local grant for A may explicitly raise or lower A's maximum.
No repository can raise the remaining depth it received.

### Delegation manifests

A version 1 `geas.yaml` may add one root-level `delegations` object containing
`path`, `sha256`, and `size_bytes`. The path must be the normalized relative name
`geas-delegations.yaml`; catalog verification covers the exact bytes and size.
The referenced strict manifest has `version: 1` and a sorted `delegations` list.
Each list item uses the same `subject`, `capabilities`,
`delegable_capabilities`, `resources`, `max_delegation_depth`, and `expires_at`
fields as a local grant, but omits `decision`, `created_at`, and `created_via`:
a delegation entry can only be an allow intersected with its parent. It
contains:

- child repository identity;
- allowed Git refs, ontology paths, and optional bundle SHA-256 selectors;
- a subset of capabilities;
- a subset of resource scopes;
- an expiry time or explicit null;
- the child's remaining delegation depth; and
- descriptive metadata that has no authorization effect.

A delegation is inert unless the parent has effective `trust.delegate`
authority. Its effective grant is the intersection of:

1. every parent grant in the chain;
2. the parent's remaining delegation depth;
3. the child manifest entry;
4. the winning applicable root-local decision; and
5. the requested operation, resource, ref, path, and digest.

An empty intersection is a denial. To traverse an edge, the parent effective
grant must contain `trust.delegate`, the child's requested capabilities must be
within the parent's effective `delegable_capabilities`, the child repository
must be in the parent's effective `delegated_repositories`, and the parent's
remaining depth must be greater than zero. After traversing that edge, the
child's effective remaining depth is exactly:

```text
min(parent_effective_remaining_depth - 1, child_declared_max_delegation_depth)
```

The child's effective `delegable_capabilities` is the intersection of the
parent's effective delegable set, the child's capabilities, and the child's
declared delegable set. Thus a root depth of `1` permits `A -> B` and gives B
remaining depth `0`; it cannot permit `B -> C`. Cycles, repeated repository
identities in a chain, expired grants, unknown capabilities, malformed refs,
digest mismatches, ambiguous repository normalization, or any attempted
widening fail closed.

### Deterministic decision order

Each request names an authority-origin repository and an operation-target
repository; they are identical for direct authority. For each requested atomic
capability, Geas:

1. normalizes both repositories plus the ref, path, digest, connector, host, and
   target;
2. rejects malformed or unsafe input before grant matching;
3. evaluates matching local rules for a repository context using the existing
   selector specificity order: digest, path, then ref;
4. applies capability and resource specificity within the same selector score
   and resolves an equal-specificity allow/deny tie to deny;
5. denies every route to a target whose winning target-local decision is deny;
6. treats a winning target-local allow as a direct candidate authorization;
7. separately enumerates allowed origin-local grants whose delegated-repository
   scope can reach the target;
8. resolves their delegation paths in sorted repository/manifest order,
   aborting a path when any intermediate repository has a winning local deny;
9. intersects capabilities, delegable capabilities, resources, expiry, and
   decremented remaining depth at each hop; and
10. selects the lexically first valid candidate chain and emits one canonical
    decision receipt, or emits a durable denial record if no chain is valid.

A matching local allow on an intermediate repository is an additional
intersection bound. No matching local rule on an intermediate repository leaves
the already-delegated bound unchanged. Thus a specific local allow may override
a broader local deny under the existing specificity rules, while no delegated
allow can override the winning local denial for its repository context.

An operation requiring multiple capabilities proceeds only when every required
capability is allowed. The receipt records the normalized request, result,
matching local rule identities, manifest hashes, Git commits, delegation chain,
effective constraints, evaluator version, and canonical receipt SHA-256. It
contains no secrets or source excerpts.

`--yolo` continues to answer only unresolved `repository.read` prompts for the
current invocation. It never grants delegation, source fetch/archive, external
model use, publication, direct push, or knowledge promotion.

## Declaring source intent

### `build.yaml` extension

An ontology's catalog-pinned `build.yaml` may contain a sorted `source_intent`
list. Each entry is strict and non-authoritative:

```yaml
source_intent:
  - id: issuer-news-example
    role: issuer_news
    discovery:
      kind: rss_atom
      locator: https://example-miner.com/news/feed.xml
    allowed_hosts:
      - example-miner.com
    allowed_path_prefixes:
      - /news/
    accepted_media_types:
      - application/atom+xml
      - application/pdf
      - text/html
    document_patterns:
      - /news/*.pdf
    refresh:
      interval_seconds: 900
      max_items: 40
      max_depth: 1
    required: true
    priority: 10
    associations:
      concepts:
        - concept:example-miner
      topics:
        - Canadian gold miners
    temporal:
      field: published_at
      retention: append_only
```

Supported discovery kinds in the first release are:

- `direct_url`;
- `rss_atom`;
- `sitemap`;
- `https_html` link enumeration within a declared page; and
- authorized Mojeek result acquisition.

Supported acquisition media are bounded HTML, PDF, JSON, XML, RSS, Atom, and
plain text. JSON and XML are preserved as original bytes and receive typed
deterministic text derivations. RSS/Atom and sitemaps yield candidate records;
they do not make linked content trusted. Common Crawl remains a later adapter
unless added explicitly to the implementation plan.

Network phases require these capabilities:

| Action | Required capabilities |
|---|---|
| Materialize an already declared direct-URL candidate without I/O | none |
| Query Mojeek or another metadata-only discovery API | `source.discover` |
| Retrieve and enumerate RSS/Atom, sitemap, or HTML discovery bytes | `source.discover` + `source.fetch` |
| Persist discovery response bytes beyond allowed transient metadata | `source.archive` in addition to the preceding capabilities |
| Retrieve a selected source document | `source.fetch` |
| Persist a selected source document | `source.fetch` + `source.archive` |
| Parse, structure, index, or select anchors from persisted bytes | `source.extract` |
| Send selected data to an external model | `model.external` plus existing model-policy and budget approval |

Fetching a feed does not authorize fetching any item it names. Each child item
is normalized and authorized as a separate source-document request.

Every locator and discovered child URL must match both the checked-in intent
and the effective local resource grant. A source declaration cannot broaden
its grant by naming more hosts or paths. Empty or absent source intent preserves
current behavior.

### Source work state machine

The GitHub-specific ontology-build loop is generalized to immutable
`SourceWorkItem` records:

```text
candidate
  -> authorized
  -> fetched | not_modified | access_constrained
  -> archived
  -> parsed | parser_constrained
  -> structured
  -> indexed
  -> anchors_selected
  -> extraction_proposed | extraction_constrained
  -> finalized
```

Each transition is a small deterministic unit with an atomic checkpoint. Its
identity includes the ontology bundle digest, source-intent ID and canonical
bytes, normalized locator, relevant validator/parser/connector versions,
effective capability receipt, and immutable predecessor identity. Re-running a
completed compatible unit reuses its result. An incompatible configuration or
source version creates a successor record; it never mutates history.

Repository snapshots enter this state machine after `fetched` through a
`github-repository` adapter. The current README extraction path is retained as
that adapter's initial document selector, then can expand only through separately
authorized catalog or source intent.

### Bounded fetching

The existing pinned HTTPS fetcher remains the base security boundary and is
extended with injectable deterministic request/response handling for:

- DNS rebinding checks before every request and redirect;
- public-address-only resolution, with IPv6 covered as strictly as IPv4;
- HTTPS-only destinations and default ports;
- credential-free URLs;
- redirect, timeout, response-size, decompression-size, and content-type limits;
- conditional requests with `ETag` and `Last-Modified`;
- explicit handling of `200`, `304`, `Retry-After`, and terminal errors;
- a bounded per-source and per-run request ledger;
- content sniffing before parser selection; and
- immutable request metadata without credentials or raw response headers.

Redirect destinations must independently satisfy source intent and effective
local grants. Mixed public/private DNS results fail closed. Unsupported media,
robots or access denial, authentication requirements, JavaScript challenges,
licensing uncertainty, and exhausted retry budgets become typed
`AccessConstraint` records. Geas does not evade them. A human may lawfully
deposit a document through the existing deposit workflow.

### Storage, licensing, and extraction

`source.fetch` permits a transient response only. Original bytes are persisted
only when `source.archive`, retention policy, storage rights, license handling,
and size limits all permit it. An eligible `200` creates a new immutable source
version unless the bytes already exist. `304` creates a refresh observation
bound to the earlier version. Discovery snippets remain leads and never become
evidence.

Archived versions flow through existing parser isolation, structural anchors,
citation derivation, threat scanning, and source-library snapshot building.
Only affected sources and their indexes are rebuilt. Anchor selection remains
outside the model. Extraction is proposal-only and requires `source.extract`;
external providers additionally require the exact `model.external` grant plus
the existing model policy, data class, budget, call, and token authorization.

News versions are append-only observations with publication, observation,
valid, and recorded times where available. Newer reports do not overwrite old
claims. Deterministic temporal relations may mark a fact as superseded, but
acceptance still uses the Git promotion boundary.

### Refresh behavior

`geas ontology-update NAME` evaluates source intents whose configured interval
is due. It may be invoked repeatedly by an agent, cron, systemd, launchd, or
GitHub Actions; Geas itself does not require a resident scheduler. The command:

- processes due intents in priority then UTF-8 ID order;
- enforces ontology and local-policy request/time/byte/model ceilings;
- uses a fakeable clock for every scheduling decision;
- resumes compatible checkpoints after interruption;
- reserves a finalization window;
- emits progress on stderr and a canonical JSON receipt on stdout; and
- exits non-zero with actionable status when a required route is incomplete.

An optional source failure is recorded and does not prevent deterministic
finalization. A required source failure preserves its knowledge gap and marks
the run incomplete. No retry loop is unbounded.

## Agent bootstrap and repository installation

### Static instructions remain useful

The generic Geas skill and every ontology skill will begin with a concise
decision tree:

1. If `geas` is available, verify its identity and use its deterministic CLI.
2. If a repository contains `.agents/skills/<name>`, the checked-in snapshot is
   readable without Geas.
3. If Geas is absent and installation is desired, use the pinned project command
   shown below; installation is never silently forced.
4. For a repository-backed ontology, use the recorded repository URL, ref,
   catalog path, ontology name, and bundle digest.
5. Read only the reference page needed for the current question.

Generated skills preserve external source URLs and `geas` retrieval commands.
They do not bundle every original document. Source links are provenance, not an
instruction or a claim that access, safety, license, freshness, or completeness
is guaranteed.

### Installation command

The documented software bootstrap is pinned to an operator-approved Geas
commit:

```bash
uv tool install \
  --from git+https://github.com/Epiphytic/geas.git@<operator-approved-commit> \
  geas
geas config-init
```

The authority for first installation is the user's explicit request or a
pre-existing agent policy that names the exact Geas repository and commit. A
commit found only in an untrusted skill or repository is not approval. Before
execution, the agent resolves the supplied ref to one commit, displays the
normalized project URL and full object ID, and states that it is about to
execute packaging code from those bytes and create trusted local configuration.
The full object ID provides immutability, not authorship. If no operator-approved
commit or ref exists, the agent leaves the static skill usable and asks for one;
it must not substitute the current default branch silently. The skill also
links to the project repository for operators who want to inspect or choose
another install method. It must not present installation as required to read a
checked-in skill.

### Repository transaction

Two new entry points provide the common repository-backed workflow:

```bash
geas repository-install NAME URL \
  --ref refs/heads/main \
  --trust-repository \
  --link

geas repository-install \
  --current-repository \
  --trust-repository \
  --link
```

The command announces each planned mutation on stderr, then performs:

1. normalize the remote, ref, catalog path, and destination;
2. fetch or inspect the exact Git object with hooks and credential helpers
   confined;
3. verify the cumulative `geas.yaml` catalog and closed hash inventory;
4. display the repository identity, exact commit, ontologies, capabilities
   requested, and trust effect;
5. record repository trust only because `--trust-repository` explicitly asked
   for that local mutation;
6. create a named subscription or bind the verified current checkout;
7. hydrate verified projection artifacts where available;
8. install or update the managed generic Geas skill;
9. export selected ontology skills;
10. place repository-scoped snapshots in `.agents/skills` when trackable and
    create only detected managed links for Codex, Claude, and OpenCode;
11. write and fsync an ownership/phase receipt; and
12. return exact update and removal commands.

For this command, `--trust-repository` has one deterministic, inspectable
meaning. It creates a branch-specific local grant for the verified repository
and all current catalog ontology paths with:

- `repository.read` and `trust.delegate`;
- delegation depth `1` unless `--delegate-depth N` is supplied;
- `source.discover`, `source.fetch`, `source.archive`, and `source.extract`
  limited to the hosts, path prefixes, connectors, and delegated repositories
  present in the currently verified source-intent and delegation manifests; and
- no provider/model or Git-write capabilities.

Its `delegable_capabilities` contains `repository.read` and the four listed
source capabilities. It also contains `trust.delegate` when the selected depth
is greater than one, allowing each traversed child to receive only the
decremented remainder. The resource set contains only child repositories and
source scopes present in the exact verified manifests at installation time.

Consequently, a later repository update may narrow or reuse the grant but
cannot silently add a new host, connector, child repository, model, or write
target. Such an expansion is denied until the operator records a new local
grant. `--read-only` may be used instead of `--trust-repository` to persist only
`repository.read`. Operators who want a narrower custom grant omit both flags
and configure or approve the exact capabilities separately. The JSON receipt
includes the complete local grant before it is committed.

If `.agents/skills` is ignored, the existing trackable `.geas/skills` fallback
and relative-link behavior applies. A repository snapshot is copied into the
repository so agents without Geas can use it; user-scoped and agent-specific
locations link to that canonical copy when appropriate.

The transaction stages changes before atomically installing them. A failure
before the configuration commit removes staging. A failure after a committed
phase leaves a resumable receipt and never guesses at rollback ownership.

Bootstrap mutation authority is intentionally distinct from delegated content
authority:

| Mutation | Required direct invocation |
|---|---|
| Install Geas software | The operator-approved `uv tool install` command |
| Create managed config defaults and generic skill | `geas config-init` |
| Clone/bind a repository, create a subscription, and export/link managed skills | `geas repository-install` with the named destination/options |
| Persist repository/source trust | `--trust-repository`, `--read-only`, an interactive approval, or a prior local grant |
| Change delegation depth | `--delegate-depth N` with `--trust-repository`, or a manual local config edit |
| Update owned checkout and skills | `geas repository-update NAME` |
| Remove owned checkout, trust, subscription, skills, and links | `geas repository-remove NAME` |
| Publish remotely | A separate effective Git capability and publication flag |

These explicit commands authorize only their documented, path-confined local
mutations. They do not authorize source/model/network work or remote Git writes;
those still require capability decisions. A repository file, generated skill,
model response, update hook, or source document cannot invoke or widen a
bootstrap transaction.

`geas repository-update NAME` re-verifies software provenance, synchronizes the
exact subscription ref, re-evaluates capabilities and catalog hashes, refreshes
due sources when authorized, regenerates owned skills, and optionally publishes
the deterministic changes. `geas repository-remove NAME` removes only paths,
links, subscriptions, trust entries, and generated branches recorded as owned by
that installation receipt. Modified or ambiguous paths fail closed unless the
operator supplies the existing explicit force mechanism. Removing a repository
installation does not uninstall Geas itself; the receipt states the separate
`uv tool uninstall geas` command for an operator who wants it.

## Publishing repository changes

Generated paths are classified before staging. The classifier uses normalized
repository-relative paths plus strict artifact manifests; a receipt cannot label
an arbitrary path as generated.

| Path role | Local only | Pull request | Direct push to non-canonical topic branch | Direct push to canonical ref | Artifact auto-merge |
|---|---:|---:|---:|---:|---:|
| Generic and exported skill snapshots/manifests | yes | `git.pull_request` | `git.direct_push` | `git.direct_push` | `git.auto_merge` |
| Deterministic projections, RDF exports, generated indexes, and generated docs | yes | `git.pull_request` | `git.direct_push` | `git.direct_push` | `git.auto_merge` |
| Runtime stores, downloaded originals, logs, credentials, or SQLite caches | no commit | forbidden | forbidden | forbidden | forbidden |
| Extraction proposals and candidate bundles outside canonical promotion paths | yes | `git.pull_request` | `git.direct_push` | forbidden | forbidden |
| Promotion manifests, accepted ontology records, source cards, or policy files | yes | `git.pull_request` | `git.direct_push` | `git.direct_push` + `knowledge.auto_promote` | `git.auto_merge` + `knowledge.auto_promote` |
| Unclassified or operator-authored paths | untouched | forbidden | forbidden | forbidden | forbidden |

`knowledge.auto_promote` never authorizes a Git operation by itself. It is an
additional gate when automation would make semantic bytes reachable from a
canonical ref. The existing promotion verifier still decides whether a
promotion manifest is valid; the capability does not bless its contents.

### Pull requests are the default

When an update creates repository changes, the default publication mode is:

```text
--publish pull-request
```

This mode requires effective `git.pull_request` authority for the exact
repository and target ref. It creates or updates a deterministic branch, commits
only receipt-owned paths, pushes with an exact lease, and opens or updates one
PR. Branch name, commit message, title, and body derive from canonical receipt
identities so retries converge. Dirty unrelated files are never staged.

`--publish none` leaves reviewed local changes and reports them. It performs no
remote mutation.

### Direct push is explicit

Direct push is supported but never inferred from agent installation,
`--trust-repository`, a catalog, a skill, `push_on_update`, or a broad repository
read grant. It requires all of:

1. an effective root-local `git.direct_push` capability for the exact repository
   and target ref;
2. a writable branch ref;
3. the explicit invocation flag `--direct-push`;
4. a clean, verified base and only receipt-owned generated paths;
5. a fresh remote-head comparison; and
6. an exact lease.

Delegated `git.direct_push` is honored only when every grant in the chain
includes it in both `capabilities` and `delegable_capabilities`. The root-local
grant must therefore explicitly name it twice and include the exact child
repository and Git ref in its resource bounds. A repository manifest can never
create it. Non-fast-forward state or a changed remote head preserves the local
commit and emits a recovery command instead of rewriting history.

### Deterministic artifact auto-merge

The recommended unattended workflow uses an independent GitHub App identity to
approve and enable auto-merge for PRs containing only deterministic managed
artifacts. Eligible default paths are the generic Geas skill, exported ontology
skills, and their canonical manifests. A protected workflow must:

- run read-only generation and tests on the exact PR head first;
- trigger the privileged phase from protected default-branch code;
- reject fork PRs and untrusted workflow identities;
- re-query the open PR and exact head SHA before every mutation;
- download only the expected manifest-bound artifact;
- verify byte identity and the allowed path set without executing PR content;
- exchange GitHub OIDC for a short-lived, repository-specific App token through
  `octo-sts-rust`;
- approve using an identity distinct from the authoring identity;
- enable auto-merge only when required checks and rulesets still pass; and
- avoid `pull_request_target` checkout or execution with a write token.

The existing Geas identity is
`Epiphytic/.github:.github/chainguard/geas-pr-skill-sync.sts.yaml`. Its protected
workflow subject and repository IDs remain pinned; its production policy becomes
exactly:

```yaml
issuer: https://token.actions.githubusercontent.com
subject: repo:Epiphytic@228616596/geas@1320458746:ref:refs/heads/main
claim_pattern:
  repository_id: '1320458746'
  event_name: workflow_run
  workflow_ref: 'Epiphytic/geas/\.github/workflows/pr-skill-writeback\.yml@refs/heads/main'
permissions:
  contents: write
  pull_requests: write
repositories:
  - geas
```

The STS token uses `contents: write` only for exact managed-path write-back and
merge, and `pull_requests: write` only for approval and auto-merge. Actions,
checks, metadata, contents, and pull-request reads occur before token exchange
through the workflow's ordinary read-scoped token. A deployment that separates
write-back from approval should use two identities with correspondingly narrower
permissions. The implementation verifies these API requirements with
fixture-backed contract tests and documents the policy alongside the workflow.
Tokens are never exposed to PR-controlled processes.

Knowledge promotion PRs are excluded from this default. Automatic approval or
merge of a verified promotion requires a separate effective local
`knowledge.auto_promote` capability for the ontology and canonical ref. This
preserves the distinction between reproducible generated views and semantic
knowledge acceptance.

Documentation will include GitHub App creation, installation on selected
repositories, `octo-sts-rust` deployment and identity policy, ruleset and
required-check configuration, fork behavior, audit verification, credential
rotation, and removal. Forge automation is recommended, not required; direct
push and local-only modes remain available under their own authority.

## Receipts, errors, and recovery

Every operation writes a strict canonical receipt containing only normalized
identities, selected capabilities, hashes, phase results, owned paths, Git
objects, and recovery commands. Receipts are stored beneath the trusted local
configuration root or runtime store, never taken from the ontology repository.

Phase receipts exist for:

- capability resolution;
- discovery;
- fetch and refresh;
- archive;
- parse and structure;
- library snapshot and anchor selection;
- extraction proposal;
- software bootstrap;
- subscription/trust mutation;
- skill installation/linking;
- branch/commit/PR creation;
- direct push; and
- removal.

On interruption, a rerun verifies the completed phase's identity before reuse.
If verification fails, Geas stops and identifies the conflicting state. It does
not silently regenerate canonical inputs or bless later-layer data. Publishing
failure preserves the exact local branch and commit. Removal uses journals and
exact identity checks before deleting or unlinking anything.

## Deterministic verification strategy

All normal tests remain offline. They use temporary roots, local bare Git
repositories, fixture HTTP transports, fake DNS, fake clocks, fixture model
clients, and fixture forge APIs.

### Capability and delegation tests

- normalization and canonical serialization for every selector and resource;
- compatibility conversion of existing `trust_rules`;
- one-hop default and per-repository depth overrides;
- multi-hop intersection without widening;
- delegation-capability intersection and exact depth decrement at every edge;
- ref, directory, repository, and ontology-digest scopes;
- expiry boundaries with a fake clock;
- local deny precedence and equal-specificity deny ties;
- cycles, repeated identities, ambiguity, unknown capability, bad ref, bad
  digest, dirty checkout, and hash-pinned manifest rejection;
- deterministic grant-chain receipt bytes independent of input ordering; and
- proof that `--yolo` grants only invocation-scoped `repository.read`.

### Acquisition tests

- direct URL, HTML, JSON, XML, RSS/Atom, sitemap, PDF, plain-text, Mojeek, and
  GitHub repository adapters;
- exact host/path/media-pattern intersection with local grants;
- DNS rebinding, mixed public/private results, IPv4/IPv6, credential-bearing
  URLs, non-HTTPS URLs, unsafe redirects, port changes, redirect loops, size,
  decompression, timeout, and media-type rejection;
- `200`, `304`, `ETag`, `Last-Modified`, `Retry-After`, permanent failure, and
  duplicate feed-item behavior;
- license/storage-rights denial with proof that no archive write occurred;
- content-addressed idempotence and immutable successor versions;
- parser and anchor identity, exact quote verification, citation derivation,
  threat handling, and temporal supersession;
- source-library incremental rebuild and bounded context selection;
- model policy, budget, and capability denial with proof that no model call
  occurred;
- required versus optional source finalization; and
- interruption/resume at every state transition.

### Bootstrap and publication tests

- absent Geas instructions, already-installed Geas, incompatible provenance,
  and no-forced-install static-skill behavior;
- repository URL/ref/catalog normalization and closed-inventory verification;
- install, idempotent reinstall, update, conflict, interrupted recovery,
  unlink, remove, and precise ownership rollback;
- `.agents/skills` snapshot behavior, ignored-path fallback, and Codex/Claude/
  OpenCode detection and link deduplication;
- PR default, `--publish none`, and explicit direct-push gates;
- denial when only `repository.read`, `git.pull_request`, or a repository
  manifest requests direct push;
- exact branch/commit/PR retry convergence and remote-head lease failures;
- deterministic-artifact auto-merge eligibility versus
  `knowledge.auto_promote` separation;
- protected-workflow event, head, repository, artifact, path, App identity, and
  permission validation; and
- fork PR rejection with proof that no token exchange or write occurs.

### Integration acceptance

A fixture-backed Canadian gold-miner ontology exercises the complete vertical
slice:

1. subscribe to a local ontology repository;
2. resolve a one-hop delegated official-source grant;
3. ingest issuer news, a regulatory filing, and a structured financial response;
4. record one not-modified result and one access constraint;
5. build the source library and exact anchors;
6. create proposal-only management and financial-health extractions;
7. interrupt and resume without duplicate calls or records;
8. export a deterministic repository-scoped skill;
9. create a deterministic PR publication receipt; and
10. remove the installation without touching unrelated files.

CI runs focused unit suites in parallel, then this integration contract, the
maintained open-source-research-agents demo, Ruff, the full offline test suite,
and `git diff --check`. No normal CI test requires live network access, a live
forge, credentials, or a real model.

## Parallel delivery streams

One initial Bead owns a shared-contract commit. No feature stream starts before
that commit lands. It adds only strict protocol types and fakes, with no live
effects:

- `capabilities.py`: `Capability`, `CapabilityRequest`, `CapabilityDecision`,
  `CapabilityGrant`, `DelegationManifest`, and `CapabilityEvaluator` protocol;
- `source_intent.py`: `SourceIntent`, discovery/resource/refresh models, and
  `SourceAdapter` protocol;
- `source_work.py`: `SourceWorkItem`, transition/checkpoint/receipt models, and
  work-store protocol;
- `bootstrap_models.py`: repository-install phase, ownership, recovery, and
  mutation receipt models;
- `publishing.py`: path-role, publish-request/result models, and publisher
  protocol;
- `tests/fakes/`: deterministic evaluator, adapter, work store, publisher,
  clock, DNS, HTTP, model, and forge implementations; and
- contract-version constants and canonical serialization tests for every shared
  model.

Those modules are exclusively owned by the shared-contract Bead until the first
fan-in. Interface changes after that point require a dedicated contract-change
Bead and updates to all affected fakes in the same commit. With those interfaces
fixed, implementation is split into independently owned Beads streams:

1. **Capability graph and delegation** — local grant migration, evaluator,
   delegation manifests, depth/cycle/expiry handling, and receipts.
2. **Source intent and network adapters** — strict source models, conditional
   fetcher, feeds, sitemaps, HTML/JSON/XML adapters, security limits, and access
   constraints.
3. **Generalized ontology source work** — state machine, checkpoints, GitHub
   adapter migration, incremental libraries, anchors, extraction, refresh, and
   temporal records.
4. **Agent bootstrap lifecycle** — generic and generated skill text,
   repository install/update/remove, detected links, transaction ownership, and
   recovery.
5. **Publishing and forge automation** — PR default, explicit direct push,
   GitHub App/Octo STS protected workflows, auto-merge eligibility, and docs.
6. **Integration, security, and documentation** — gold-miner fixtures,
   end-to-end acceptance, invariant/adversarial review, CI fan-in, and operator
   guides.

Streams 1, 2, 4, and 5 begin in parallel after shared contracts. Stream 3 also
begins then against evaluator and adapter fakes; its unit commit is independently
mergeable, while its live-adapter integration Bead depends on Streams 1 and 2.
Stream 4 uses the fake evaluator and publishes no remote changes. Stream 5 uses
fake bootstrap ownership receipts; its integration Bead depends on Streams 1
and 4. Stream 6 begins fixtures and documentation in parallel, then its
end-to-end Bead depends on the live-integration Beads from Streams 1–5. Each
Bead owns a non-overlapping file list and must leave the full existing suite
passing; agents must not revert other stream changes. Fan-in Beads run focused
cross-stream contract tests before the next dependency layer.

The implementation plan will encode these streams as a Beads dependency graph,
with small reviewable tasks and explicit fan-in gates rather than one serial
checklist.

## Compatibility and migration

- Existing `geas.yaml` files without delegation declarations remain valid.
- Existing `build.yaml` files without `source_intent` retain current behavior.
- Existing `trust_rules` keep their current repository-read semantics and are
  normalized into the evaluator without gaining new capabilities.
- Existing named subscriptions, immutable snapshots, `skill-export`,
  `skill-update`, `skill-unlink`, and `skill-remove` remain supported.
- Legacy `ontology_git.push_on_update` does not authorize direct push; use of it
  after migration requires a matching capability and explicit invocation, and
  documentation will mark the field deprecated if implementation evidence
  permits removal.
- Existing generated skill manifests receive a version bump only when the new
  bootstrap or repository metadata is rendered. Old static snapshots remain
  readable and removable under their recorded version rules.
- Receipt and checkpoint schema versions are explicit. Unsupported future
  versions fail closed rather than being partially interpreted.

## Security invariants

Implementation is acceptable only if all of these remain true:

1. Retrieved or model-generated content cannot choose tools, destinations,
   credentials, capabilities, budgets, transitions, or writes.
2. A repository declaration cannot grant more authority than trusted local
   configuration, directly or through delegation.
3. Delegation can only narrow capability, resource, expiry, and depth.
4. `--yolo` cannot authorize acquisition, persistence, model use, publication,
   direct push, or knowledge promotion.
5. Direct push always requires a local capability and an explicit invocation.
6. Deterministic artifact auto-merge cannot accept semantic knowledge unless a
   separate local `knowledge.auto_promote` grant exists.
7. Privileged CI never executes PR-controlled bytes with its write token.
8. Every accepted claim still traces to immutable source bytes and exact
   selectors through a verified promotion.
9. Source, license, threat, dissent, gap, and temporal context remain visible.
10. Failure or interruption leaves an inspectable, resumable state and never
    widens authority.
11. Removal affects only exact receipt-owned state.
12. Canonical Git bytes, immutable history, truth snapshots, projections,
    skills, and answers remain distinguishable layers.

## Completion criteria

The feature is complete when the documented commands and schemas are
implemented, all offline deterministic suites pass, the Canadian gold-miner
fixture demonstrates automatic retrieval through repository skill publication
and removal, generated instructions work with and without an installed Geas,
and security tests prove that repository/model text cannot grant acquisition or
Git authority. Deployment of a real GitHub App or live source credentials is an
operator step, not a prerequisite for deterministic feature correctness.
